## Context

MiniAEC 目前已经有离线 AEC 验证代码和无窗口 Tauri 托盘壳，但尚无 Windows 虚拟音频驱动或实时输出边界。本变更只建立确定性用户态 PCM 到 `MiniAEC Microphone` 的数据通路，使后续实时引擎可以依赖一个项目自有且可替换的虚拟麦克风 transport，而不把 SysVAD、WaveRT 或控制设备类型泄漏到音频引擎接口之外。

Microsoft SysVAD 是 WDM/WaveRT 虚拟音频驱动样例，不直接提供 MiniAEC 所需的用户态 PCM 注入协议。驱动原型同时涉及内核安全、实时欠载、设备生命周期、测试签名和会改变本机状态的部署验证，因此需要先形成独立的可回滚验证切片。

## Goals / Non-Goals

**Goals:**

- 固定并追踪唯一的 Microsoft SysVAD 上游、许可证和本地差异。
- 在相同输入、格式、持续时间和观测指标下比较私有 WaveRT render sink 与受限共享环形缓冲。
- 选择一个方案并建立最小的确定性 PCM 发送端、驱动数据通路和公开采集端点。
- 定义连续采集、发送端消失与恢复、驱动重启和卸载后的确定性行为。
- 把所有系统级动作限制在明确批准的本机开发验证流程中。

**Non-Goals:**

- 不建立物理麦克风、render loopback、AEC3 或托盘到驱动的数据链路。
- 不承诺生产级低延迟、功耗、多会话仲裁、自动更新、正式签名、HLK 认证或安装器体验。
- 不修改 SysVAD 之外的 WebRTC/AEC 依赖，也不使用私有录音作为测试输入。

## Decisions

### 1. 固定单一 SysVAD 上游

唯一上游为 `https://github.com/microsoft/Windows-driver-samples` 的 `audio/sysvad`，固定 commit `2ee527bfeb0aeb6be11f0a8b6dce4011b358ce89`，许可证为 Microsoft Public License（MS-PL）。实现时必须在 `driver/windows/UPSTREAM.md` 记录仓库、目录、commit、获取日期、许可证文件、导入文件清单、构建工具版本和每一项本地修改；仓库中必须保留许可证与通知要求所需的文本。

`microsoft/audio` 中的 SysVAD 副本不作为第二上游，也不参与自动同步。这样可以避免两个官方副本产生不明确的合并基线；未来升级必须是单独的显式变更。

### 2. 用同一个垂直切片比较两种 transport

两个候选方案都使用相同的 48 kHz、单声道、16-bit little-endian PCM 确定性信号、相同的帧序号标记、相同的五分钟连续运行窗口和相同的 Windows 录音工具检查。比较记录至少包含：是否只暴露一个公开 capture 端点、发送端权限、端到端连续性、可观测延迟、欠载语义、发送端重连、驱动复杂度、内核攻击面和后续 Rust 引擎接入成本。

- 方案 A：用户态发送端通过 WASAPI 写入不向普通录音或播放应用暴露的私有 WaveRT render sink，驱动把 render 流转发到公开 capture 端点。只有在该 sink 能保持私有、无需脆弱的设备枚举技巧、并满足恢复语义时才能入选。
- 方案 B：驱动提供带访问控制的控制设备，发送端通过由驱动拥有的有界共享环形缓冲写入 PCM，capture 路径按音频时钟消费。验证原型只允许 SYSTEM 或 Administrators 打开控制接口，不创建可被任意进程打开的全局命名共享内存；生产身份与服务模型留给后续变更。

先实现两个最小可测 spike，再保存一份包含数据和结论的决策记录。方案 A 在满足全部门槛时优先，因为它复用 Windows 音频栈的流控和格式协商；如果无法可靠隐藏 render sink、无法得到确定欠载/重连语义或需要不稳定的枚举依赖，则选择方案 B。不得把两套 transport 同时保留为产品路径，未选方案的原型必须与生产构建隔离。

### 3. 使用项目自有 transport 边界

用户态最小发送程序只依赖项目定义的 `VirtualMicrophoneSink` 语义：协商固定格式、写入带单调帧序号的 PCM、报告写入失败和显式关闭。WaveRT 设备标识、IOCTL、共享内存布局和 SysVAD 类型只存在于所选 Windows adapter 中，未来实时 AEC 引擎可以替换测试信号而无需感知驱动实现。

测试发送程序生成可审计的合成信号，不读取物理麦克风或 `artifacts/`。信号包含稳定基音、周期性可识别标记和单调帧序号对应的日志，以便把 Windows 录音结果与发送端时间线对齐。

### 4. 以音频时钟消费并定义欠载和溢出

公开端点名固定为 `MiniAEC Microphone`，原型格式固定为 48 kHz 单声道 PCM16。驱动 capture 路径必须按 WaveRT/音频时钟持续推进，不能由用户态写入节奏直接驱动。

发送端未连接或数据欠载时，capture 输出零值静音且时间线继续推进，不能重复旧音频。缓冲写满时拒绝最旧帧之后的新写入或按实现记录的单一策略丢弃，但必须增加可观测计数器并保持内存安全；比较阶段必须选择并固定一种策略。发送端重连从新的会话代号和帧序号开始，驱动不得拼接上一次会话的残留 PCM。

### 5. 把恢复边界分为发送端、驱动和录音客户端

发送程序退出时，已经打开的 Windows 录音流应继续收到静音；发送程序重启后同一录音流应恢复收到新会话信号。驱动被禁用、启用或重启时，现有录音流可以失败并由 Windows 录音工具重新打开，但端点重新出现后必须再次可采集。卸载后 `MiniAEC Microphone`、控制接口、驱动服务和临时驱动包不得残留，其他物理音频设备不得被改变。

### 6. 测试签名只用于明确批准的开发机操作

构建产生 x64 Debug 驱动包、目录文件和本地测试证书签名结果。证书私钥、生成的驱动包和机器特定部署产物不提交到仓库。启用 Windows 测试签名、安装、禁用/启用设备、重启驱动和卸载都必须在执行前得到用户明确批准；脚本默认只检查前置条件或打印将执行的命令，不静默修改启动配置、证书存储或设备状态。

开发验证记录必须包含 Windows、Visual Studio、SDK、WDK、Secure Boot/测试模式状态和实际执行命令。正式签名、服务化权限模型和生产安装器作为后续变更处理。

## Risks / Trade-offs

- [私有 WaveRT sink 仍被普通应用枚举] → 把“系统中只出现一个公开 `MiniAEC Microphone` capture 端点”设为硬门槛，失败即转向受限共享环形缓冲。
- [共享缓冲扩大内核攻击面] → 使用固定大小、严格校验的布局，由驱动拥有映射生命周期，并把原型控制接口限制到 SYSTEM/Administrators；所有长度、索引和会话切换都做边界检查。
- [测试签名或驱动部署影响开发机启动和音频设备] → 所有变更动作需明确批准，先保存基线设备清单，提供逐步卸载与恢复检查，不自动更改 Secure Boot。
- [Windows 录音工具的编码隐藏样本级问题] → 同时保留发送端序号日志和驱动诊断计数器，用录音结果验证可听标记与持续时间，用计数器验证欠载、溢出和会话切换。
- [五分钟通过不能证明生产稳定性] → 本变更只证明最小通路；长时间漂移、压力、并发客户端和性能门槛留给实时引擎接入后的独立验证。
- [固定上游会错过安全或 WDK 修复] → 不跟随 `main` 自动更新；任何升级单独审查 release/commit 差异、许可证、构建结果和本地 patch。

## Migration / Rollback Plan

1. 在不安装驱动的情况下导入并构建固定 SysVAD 基线，记录可复现工具链和上游清单。
2. 分别构建两种隔离的 transport spike，使用合成 PCM 和非破坏性检查生成比较记录。
3. 经硬门槛选择单一方案后，将它接入项目自有 `VirtualMicrophoneSink` adapter，并从默认构建排除未选原型。
4. 经用户明确批准后，在开发机安装测试签名包，保存安装前设备基线并执行验收场景。
5. 回滚时先停止发送程序，再卸载测试设备和驱动包、移除仅为本次验证添加的测试证书，并与基线清单比较；启动配置如有改变，只按记录的原值恢复且需要再次确认。

## Open Questions

- 实现阶段需要记录本机可用的 Visual Studio、SDK 与 WDK 精确版本，并确认固定 SysVAD commit 是否无需补丁即可用该组合构建；这不改变上游 pin。
- 如果方案 A 与方案 B 都未满足公开端点、连续性或恢复硬门槛，本变更应停在比较记录并提出新的设计变更，不得用降低验收标准的方式继续。
